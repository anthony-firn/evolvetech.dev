Shipping the same site to two CDNs

I wanted this site to stay available when one hosting provider failed. GitHub Actions publishes the same static files to Netlify and Bunny. A separate monitor checks each provider and changes DNS when the primary remains unhealthy. Two failures showed why copying files was only part of the job.

See the deployment bugs →Source on GitHub ↗

What I own

The deploy scripts, provider configuration, monitor, certificate automation and verification checks live in the public website repository. I use AI coding agents for implementation and tests; I choose the operational constraints and review what is actually exercised.

The standby has its own storage origin. DNS routing does not depend on one provider proxying the other. Certificate renewal runs separately from traffic switching.

Same files, different module behavior

JavaScript modules loaded from Netlify but failed on the standby. Bunny Storage served .mjs files as application/octet-stream; browsers require a JavaScript content type for modules.

I configured a CDN edge rule for text/javascript and documented it in the deployment instructions. Identical bytes alone had not established equivalent browser behavior. The new read-only delivery check verifies a representative module on both providers after deployment.

Recorded fix and deployment note

The redesign that disabled failover

The monitor expected the homepage to contain “Useful projects.” A redesign removed that sentence, so both healthy copies were classified as unavailable and failover could not act. I changed the marker to the page title.

Source diff and failure description. The local checks now compare the real homepage with the monitor contract. A regression also exercises a page without the old marketing sentence. The title marker is still a coupling; a future title change must update the contract.

What was exercised

On October 22, a controlled primary-failure simulation changed the real DNS target to Bunny, and the site was observed serving there over HTTPS. Normal monitoring held the backup route through the configured recovery period and restored the primary. The record also checked matching hashes for eight public files on each provider.

Dated verification record · Routing tests. This was a controlled routing drill, not an independently observed provider outage or a global availability measurement.

Run the checks

cd evolvetech.dev
python3 tools/verify_portfolio.py

# Optional: read-only HTTPS probes, no provider credentials
python3 tools/check_delivery.py --live

The local command checks internal links, sitemap and metadata, routing decisions, the homepage marker, module MIME regression and the synthetic campaign-repair example. The live command checks the hostname, certificate, homepage, health document and one representative module on each provider. It makes no DNS changes.

Measurements and limits

There is no measured build-time improvement or uptime percentage on this page. The dated local check record identifies the commands, machine and elapsed times; those times are not cloud deployment timings.

DNS caches, scheduler gaps, shared domain configuration and provider control-plane failures remain dependencies. The live probe covers representative paths, not every asset or region. This website demonstrates ownership of a small delivery system, not experience operating a large CI runner fleet.
