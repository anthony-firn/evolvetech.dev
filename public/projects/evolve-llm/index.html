AI inference · Rust · WebGPU · WebAssembly

Evolve LLM

Open a page, pick a model and chat with it on your own graphics card. Models too big for the GPU still run: what fits stays on the GPU, and the rest is read from storage as each token needs it. There is nothing to install, and with web search off nothing leaves your device.

Why I built it

Running a language model locally usually means installing a runtime, drivers and a model manager, then learning which file fits your hardware. Browsers already ship a GPU programming interface. I wanted a single link that takes anyone from nothing to a private, local model in a minute, on hardware they already own, and that does not stop at the size of their GPU's memory.

Try it

Open the chat → Pick a model: SmolLM2 135M is a 145 MB first test and Qwen2.5 0.5B the recommended start. Large models are listed separately, from OLMoE (7 billion parameters) to Kimi K2 (one trillion). Files download once from Hugging Face into the browser’s private storage, part by part for split models, and load from there next time, even offline. You can also browse any Hugging Face repository or open files from your disk.

WebGPU is needed: Chrome or Edge on Windows, macOS, ChromeOS and Android; Safari 26; Firefox on Windows. On Linux, Chrome needs its WebGPU flag. The largest models also need tens to hundreds of gigabytes of free disk space for the browser to store them.

A local workspace with Pi

Open the app and select Terminal → Run file and text commands in a Rust/WASM sandbox, then load a model and enter pi followed by a task. Real Pi agent core reuses the loaded weights and displays file, shell and research tool results. Files persist in the browser and can be imported or exported.

Web access explicitly enables public searches and page reads through external providers. The workspace has no host processes or host files. It supports a bounded shell subset; small models need review. Setup, self-hosting and execution limits →

The inference engine

No machine-learning framework is involved. I wrote the GGUF parser, decoders for 25 weight formats down to 1.56 bits per weight, the transformer forward pass as WGSL compute shaders, three tokenizer families and the chat-template renderer in Rust. The same crate runs natively through wgpu on Vulkan, Metal or Direct3D 12, and compiles to a 2.5 MB WebAssembly engine for the browser’s WebGPU.

  • Dense models (Llama, Mistral, Qwen2 and 3, SmolLM) and mixture-of-experts models (Qwen3-MoE, Mixtral, OLMoE, DeepSeek V2 and V3, Kimi K2), from single or split GGUF files.
  • Expert routing with softmax or sigmoid scores, DeepSeek’s selection bias and group limit; prompts are grouped by expert so each expert’s weights are read once per 32 tokens.
  • DeepSeek’s multi-head latent attention caches one compressed vector per token, 576 values instead of 40,960, and serves four heads per cache read.
  • Weights keep their file layout on the GPU when memory is tight and use a faster expanded layout when it is not.

Models larger than the GPU

Settings give the model a GPU memory budget. The engine keeps norms, then each layer’s attention and shared weights, then the output head on the GPU as far as the budget allows. Routed experts share a cache of slots: each layer reports which experts its tokens chose, the missing ones are read into the least recently used slots, and a prompt that needs more experts than fit runs in several passes. Dense layers that do not fit stream through a pair of buffers, so one uploads while the previous one computes. The operating system’s file cache keeps recently read weights in RAM.

Streamed runs give the same replies as fully resident ones in every test. On the test laptop, OLMoE 1B-7B (2.6 GB on the GPU) replied at 15 tokens per second fully resident, and at 6 per second natively and 1.7 to 1.9 in Chrome with a 1 GB budget. Llama 3.2 1B with a 300 MB budget, reading every layer from storage for every token, replied at 1.9 tokens per second.

Web search, on your terms

Internet access is off unless you turn it on, with a Web button by the message box. Then models whose chat templates take tools can call web_search and open_url, up to three rounds per reply; other models get search results with each question. Searches go from your browser to Wikipedia and DuckDuckGo, and pages are read through Jina Reader. No server of mine sees the conversation, and each search and page appears above the answer with its sources.

Small models call tools unreliably and often answer wrongly even with good results, so treat their answers with care.

Checked against reference implementations

Speed means nothing if the numbers are wrong, so the engine is tested against independent code:

  • Dequantization of all 24 quantized and half-float formats matches gguf-py’s NumPy implementation.
  • Tokenizers match Hugging Face’s originals on 17 difficult strings for seven tokenizers, including DeepSeek V3.1 and Kimi K2, read from their GGUF headers alone. Chat prompts, including tool calls, match transformers exactly.
  • Final-token logits for SmolLM2, Qwen2.5, Qwen3 and Llama 3.2 match transformers’ float32 run on the same weights: same top token, top-20 logits within 0.2% of the range.
  • Tiny random models of each mixture-of-experts layout, converted by llama.cpp, match transformers within 0.03% of the logit range, both resident and streamed through a four-slot expert cache.
  • In Chrome under the production security policy, greedy replies match the native build word for word, including OLMoE streaming its experts.

Measured speed

I measured on a laptop running its battery power profile: an Intel integrated GPU with 15 GB of shared memory, and an RTX 3050 the profile held at its lowest clocks. Runs varied by up to a third.

  • SmolLM2 135M: 45 to 74 tokens per second in Chrome on the Intel GPU.
  • Qwen2.5 0.5B: 33 to 36 tokens per second in Chrome, and 310 to 415 prompt tokens per second natively.
  • Llama 3.2 1B: about 22 tokens per second in Chrome.
  • OLMoE 1B-7B, 7 billion parameters with 1.3 billion active: 15 to 16 tokens per second resident, and 67 to 92 prompt tokens per second natively.

Limits

This is an early release. The largest catalog models, Qwen3 235B and Coder 480B, DeepSeek V3.1 and Kimi K2, use architectures, formats, tokenizers and templates verified here, but my test laptop lacks the disk space to run them end to end, so their speed is unmeasured; expect seconds per token. Hybrid linear-attention models, the newest generation of the largest open models, are not supported yet, nor are Gemma, Phi and images. Streaming in the browser is slower than native. Speed has not been tuned against llama.cpp or WebLLM, and models can be wrong, so check anything important.
