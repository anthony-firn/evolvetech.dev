Keeping campaign data complete

At True Native Media I build and operate the integrations behind a podcast advertising workspace. One difficult failure involved data that existed in Airtable but had not reached the campaign view. Here is how I investigated it and changed the repair path.

Read the incident →Public replay source ↗

My contribution

I lead the integration work and production operations. The mirror uses scheduled publishers, resumable workers and stored pagination offsets. Retries for rate limits and transient errors use backoff and provider retry guidance. Schema checks compare stable table and field IDs and record additions, removals and type changes.

A diagnostic run on October 5, 2026 scanned 35 tables and 88,163 records. The main mirror ran every 30 minutes. Those are dated observations, not a current capacity or throughput benchmark. The mirror is TypeScript; Python is used elsewhere in the campaign-planning platform.

October 5: a current parent, missing children

A campaign confirmation could fail even when its source records existed. New child records were waiting in the synchronization queue. An unchanged parent did not guarantee that all of its referenced children had arrived.

The correction checks for missing children even when the parent content has not changed and queues a repair. The confirmation path continues rejecting incomplete campaigns instead of silently leaving records out.

Why bounded priority

The worker reserves up to eight urgent slots in a normal batch of 32, preserving room for ordinary work. Urgent checks also run between webhook pages. Repair gets a chance to run while the ordinary backlog still makes progress.

Stored cursors advance only after durable queue batches have been saved. A later-batch failure leaves the source replayable. A completed scan is distinguished from a partially fetched page; it is not safe to treat every recent timestamp as proof of completeness.

What I checked

The retained deployment record includes a source-archive hash check and checks that the intended worker configuration was preserved. Three observed batches completed 32 of 32 items, and all five affected records were subsequently verified in the operational mirror and campaign projection.

That establishes recovery for the observed incident. It does not establish whole-base parity, a cross-table transaction or sustained backlog throughput. Priority queries add bounded reads; I am not claiming a measured cost saving.

A small replay you can inspect

Download the standard-library Python example, or read its source. Run python3 campaign-freshness.py. It asserts that an unchanged parent with a missing child cannot be confirmed, schedules repair, preserves ordinary queue capacity and allows confirmation after a synthetic provider response.

The example is an in-memory explanation written for this case study. It contains invented identifiers, no customer data and none of the private worker implementation. It is not an exported production record or a performance test.
