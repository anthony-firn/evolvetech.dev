# Research brief: a valid token for the wrong service

Status: research and an offline experiment, not a published episode. Researched 2026-11-24 for the next
Proof briefing. No change to the current mission, shared style or paused creator routine.

The learning problem: an engineer protects an HTTP MCP endpoint with a JWT verifier. The signature and
issuer are correct, but the token was issued for another API. Review which component owns audience
validation and prove that the wrong token is rejected. The intended benefit is protecting user data;
this is a security/platform exercise, not a promise about hiring or pay.

## Primary material actually read

1. [MCP 2026-07-28 authorization security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations),
   complete page. The client must request the intended resource, and the server must verify that the incoming
   credential belongs to it. An upstream API requires its own credential; forwarding the incoming one is
   prohibited. These are distinct checks at different boundaries.
2. [RFC 8707, sections 1–3](https://www.rfc-editor.org/rfc/rfc8707.html), including the request examples.
   Resource identifies where a token is intended to work; scope describes access. An authorization server
   may map the resource URI to its own audience identifier. Multiple audiences are possible, but enlarge
   the trust relationship; a single resource is encouraged. Tenant-specific paths can matter.
3. [The current MCP authorization tutorial](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/authorization),
   sections Choosing an Authorization Server, implementation setup, TypeScript verifier, Opaque Tokens and
   Common Pitfalls. Read those sections, not the entire multi-language tutorial. Use an established verifier
   with the configured issuer/audience. Opaque tokens need authenticated introspection. A key-fetch outage is
   not an invalid user credential and should not force another login. `expectedResource` is not a replacement
   for validating the token's own audience. The guide also dates DCR deprecation to the July 2026 revision;
   that is context for a later episode, not today's main claim.
4. [Go SDK protocol guide, Authorization/Server and Security/Token Passthrough](https://github.com/modelcontextprotocol/go-sdk/blob/7f22059bb4b1b90709a0f6b298f8c2c9cf369c8d/docs/protocol.md).
   The documented middleware checks request credentials and can check expiry/scopes, while the supplied
   TokenVerifier remains responsible for accepting tokens issued for this server. Reading SDK code/docs
   establishes the integration boundary; choosing middleware alone does not establish correct authorization.
5. [PyJWT usage, audience/issuer/expiration and required-claim examples](https://pyjwt.readthedocs.io/en/stable/usage.html).
   The library accepts a configured audience and supports requiring claims. The locally installed library
   is 2.10.1; the currently published documentation identifies 2.15.1. The experiment records the version it
   actually ran and makes no claim about behavior in every release.

## Experiment performed

Run `python3 docs/proof-research/2026-11-25-audience-demo.py` with PyJWT and cryptography installed.
The script makes an ephemeral 2048-bit RSA key and synthetic RS256 tokens, uses no network, and prints
neither keys nor credentials. On PyJWT 2.10.1:

| Case | Observed result |
| --- | --- |
| Wrong audience, signature and issuer checked but audience disabled | Accepted: deliberate broken baseline |
| Correct audience and valid signature | Accepted |
| Wrong audience with audience checking enabled | InvalidAudienceError |
| Missing audience | MissingRequiredClaimError |
| Expired token | ExpiredSignatureError |
| Wrong issuer | InvalidIssuerError |
| Altered signature | InvalidSignatureError |
| Valid token with `other-tools:read`, required `tools:read` | Not authorized by exact scope membership |

This tests real library behavior locally, not an entire MCP authorization flow. No attack was run against
an external service. JWKS outages and downstream token handling were read in the documents but were not
exercised by this experiment.

### Opening narration sketch (unrendered)

An agent reaches a document tool. The token has a valid signature, comes from the expected issuer and
has not expired. The request still needs to fail: that token belongs to a different service.

Today you will inspect the boundary between a client, an MCP server and the API behind it. Start by
identifying who the token was issued for. Then read the protocol and the verifier's contract before
reviewing an implementation that checks the signature and stops too early.

In the exercise, you will work with claims whose signature has already been checked. A separate local
experiment signs real synthetic tokens and shows the failing case. Your task is to make the policy
visible: which request was denied, at which boundary, and why? Keep the token itself out of that evidence.
